# Reviewed graph lifecycle (development slice)

DEVELOPMENT ONLY. This includes a service-owner library conversion, separately opt-in authenticated reviewed conversion transport reusing existing upload workers, and an opt-in pending-only MCP proposal tool. It does not install live workers, grant credentials, run Gardener, or accept proposals automatically.

## Vector-only source conversion

`GraphRagApplication::enrich_uploaded_source` takes an explicit `SourceEnrichmentPlan`: canonical source ID, owner instance, request identity, opening source revision, content SHA-256, generation, original processing policy and complete target processing policy, plus confirmation. Target policy must exactly match the configured entity-enabled runtime with unchanged chunking/embedding policy. The original vector-only upload must be completed and its live source generation ready. Direct/manual entity overlays are refused.

Private `source.metadata.entity_enrichment_v1` stores the exact plan, immutable original upload origin, optional latest committed upload origin, ordered note IDs/revisions and bounded sequential entity batches (16 MiB total, max 200 chunks, max 128 entities/chunk). Provider failure never publishes mentions, changes the visible extraction policy or marks graph freshness. Identical retries resume completed batches; a dedicated owning-datastore gate prevents concurrent identical application calls repeating providers. The direct library call is not a distributed job queue; authenticated transport below uses existing durable owner leases/journals/checkpoints.

Promotion atomically fences exact source metadata/content/generation and complete source-owned note inventory, publishes all entity/mention replacements, changes the applied policy and increments a separate graph policy epoch. Source ID, URI, content generation, upload request identity, note IDs, embeddings and content remain unchanged. Source readback reports processing/extraction policy currency independently of content freshness, using a repository-backed evidence validation: bounded source-bound checkpoint, exact current chunk inventory/ownership/revisions, promotion-grade typed entity identities/scopes, complete published mentions and source/note snapshot guards in one read transaction. Metadata eligibility alone is not evidence currency. Note inspection revisions include graph policy epoch.

### Conversion cancellation publication-entry boundary

Conversion cancellation is cooperative, not a durable no-publication fence. Cancellation is checked at validation/provider/checkpoint boundaries and at the final promotion preflight; an already-entered private checkpoint may finish, but cancellation acknowledged before publication prevents promotion. Passing that final preflight explicitly enters publication (not yet the datastore commit): a cancellation observed after that point does not interrupt or reverse the repository promotion transaction. If the transaction commits, the caller receives its successful promoted result and the new graph policy epoch is committed even when its cancellation flag is now set; it must not receive a cancelled result that suggests retry is safe. A transaction error remains an error and does not publish a partial policy change.

If the caller drops or is interrupted while publication is in flight, the outcome is unknown. It must inspect the persisted enrichment stage/source policy epoch and retry the same reviewed plan to recover the persisted outcome, or use the explicit confirmed rollback path after confirming promotion. There is no cancellation acknowledgement record for this conversion, so cancellation alone never proves that publication did not commit.

`rollback_source_entity_enrichment(plan, true)` is explicit forward compensation. It restores the original applied processing policy without rewinding the latest committed upload capture, removes only the complete generated mention inventory and increments policy epoch again (no ABA revision rewind). Refuse source replacement, note drift, foreign mentions, materialized relationships or active proposal dependencies. Rejected and superseded proposals remain historical audit records, not rollback dependencies. Shared/orphan entities are retained, not globally garbage-collected.

## Future source generations

Managed enriched sources retain `graph_enrichment_managed=true`. Silent vector-only downgrade is refused. A replacement must opt into entities and supply an exact source revision. The existing durable policy-migration preparation/checkpoint/promotion machinery is reused for graph rebuilding even when processing policy itself is unchanged: last-good chunks/mentions/edges stay visible until every new chunk extraction succeeds, then source visibility and all rebuilt links promote atomically. Failed/cancelled work keeps its private stage for owner-token-fenced resume. Reviewed exact-endpoint edges are not copied to successor chunks; their evidence is superseded during successful old-generation retirement. Later generations retain the same staged-rebuild requirement.

An actual unchanged upload with a saved enrichment stage preserves the immutable original conversion lineage while updating `remote_upload` and the stage's `current_origin` to the latest committed capture. Staged, promoted and rolled-back sources retain ordinary normalized-content refresh behavior: exact Markdown, host and collection provenance can update without replacing source generation, chunks, embeddings or entities. Title and applied processing policy must remain unchanged to qualify for this path. Applied policy and complete checkpoint evidence must validate before rebinding; malformed or transplanted stages fail closed. Promotion and rollback update the active capture's applied policy, not its request identity. Public `latest_upload_request_id` names the latest capture; proof `original_request_id` names the original conversion lineage.

Unchanged publication atomically persists its canonical source revision in the job's private checkpoint. Resume and terminalization require both exact source ownership and that revision, including the graph policy epoch. Cancelled or interrupted captures that already committed remain valid source evidence, but cannot resume across a later promotion or rollback; a new explicit upload request is required. The private checkpoint is not exposed through job status. Ordinary upload restart still records interrupted work as failed and requires explicit retry; enrichment jobs alone have their separate checkpoint recovery policy.

## Exact endpoint proposal

`propose_endpoint_relationship` requires the opt-in `propose` capability. Request fields are `request_id`, exactly one `from` and one `to` (each canonical note ID, SHA-256 revision and exact nonempty content quote), `relationship`, `rationale`, `confirmed=true`. Unknown fields/cardinality expansions are rejected. Allowed relation types only: `supports`, `contradicts`, `derived_from`, `related_to`. Similarity must not be represented as causal dependency. Quotes are bounded to 2048 bytes each, rationale to 2048 bytes. Types/quotes establish a reviewed assertion, not an automatic semantic truth validator.

One transaction fences both full note/source snapshots and creates exactly one pending proposal plus one mutation receipt. No model inference, entity mutations, graph edge or automatic acceptance occurs. Request-key replay returns the same persisted outcome; changed payload under the same shared instance/request identity conflicts, including cross-operation reuse. Symmetric endpoint order is canonical. Reviewed proposal dedupe includes both immutable endpoint revisions/quotes; materialized-edge dedupe remains endpoint/type-specific.

Acceptance is separate. Remote acceptance uses the existing confirm/revision/decision capability and atomic journal. Generic service-owner acceptance for this family requires an explicit manual reviewer and uses one complete note/source/proposal-snapshot-fenced transaction (no intermediate `accepting` state). Supported note edit/policy promotion/replacement invalidates only this reviewed family and its derived edges; unrelated manually created edges are not deleted. Raw out-of-contract datastore mutation is not an authorized editing API.

## Compatibility and limitations

Schema 22 adds optional nonnegative `source.metadata.graph_policy_revision`; staging remains inside the existing flexible source metadata. Existing schema-21 stores migrate forward without a corpus scan. Older binaries must refuse the newer store. The lexical migration replay fixture now removes all subsequent migration history when manufacturing a schema20 corpus.

Default/automatic memory clients receive no new capability. Existing readers/status tool catalogs remain unchanged; `propose` exposes only creation, not `decide`/`accept`. Conversion transport is separately opt-in via enrich, never default. Exact schema22 native backup/restart qualification evidence is recorded separately; no deployment approval follows from development tests. The importer requires separate explicitly reviewed receipt adoption; local unchanged-document skip behavior is not automatically rewritten.

The synthetic off/on/on/off fixture proves one-hop accepted-edge evidence reaches a preselected fact under fixed 2/1000/400 context budgets and fixed `per_hop_decay=1.0`; this is not a default-ranking or live-corpus benchmark. It asserts edge/path/endpoint identity, positive traversal diagnostics and disappearance after explicit undo.


## Authenticated reviewed conversion transport — DEVELOPMENT ONLY

Only the new optional capability enrich exposes prepare_source_enrichment, execute_source_enrichment, read_source_enrichment_plan, get_source_enrichment_job, cancel_source_enrichment_job, retry_source_enrichment_job and rollback_source_enrichment. It grants neither upload, generic jobs, read corpus, proposal acceptance nor scans. Generic Jobs control cannot bypass enrich for a conversion. Generic job status classifies conversion and rollback as `job_type=remote_enrichment` using a database-projected family bit, without decoding or returning private saved input. Jobs-only `list_jobs` and readiness sampling omit this family; hidden jobs cannot affect readiness counts or state. Generic singular read/control aliases also require enrich for it, including damaged-plan/quarantined jobs. Jobs+enrich may observe both families, while ordinary upload status remains `remote_upload`. Bounded lists and readiness samples may contain fewer than the requested limit after filtering; they do not scan beyond that window. Authentication supplies owner; callers cannot nominate another owner. Preparation is read-only and provider-free. It returns version1 exact SourceEnrichmentPlan plus canonical JSON plan SHA256 and existing target policy SHA256. Execution requires that whole reviewed receipt, matching operation/request identity and separate confirmed=true. Unknown fields fail closed. Rollback uses a distinct request identity, same reviewed plan and exact current rollback_source_revision plus separate confirmation. No automatic cleanup of direct overlays.

Admission persists optional enrichment input in the existing remote_upload job schema and reserves the same instance/request mutation journal namespace as endpoint proposals. Exact replay returns original job; changed payload/cross-operation reuse conflicts. Source URI ownership, ordered same-document scheduling, service epoch/worker token claims, bounded server-owned worker slots, shutdown draining and terminalization recovery are reused, not forked. A conversion uses enrichment-specific phases without generation preparation or content replacement.

Conversion admission must use the reviewed plan's request ID. Rollback must use a distinct operation request ID, even if conversion happened through the direct library API and never reserved a transport journal key. Application admission rejects invalid identity before journal lookup; durable job validation enforces the same contract. A valid rollback's identical retry replays its original job.

Each private checkpoint and all-chunk publication uses the original enrichment transaction plus an exact durable job owner/epoch/token/cancellation/plan fence. Publication also commits completed job outcome in that SAME source/mention/policy transaction. Cancellation acknowledged before this transaction enters prevents publication; after commit, cancellation cannot relabel success. Unknown interrupted responses read the journal/source epoch. A dropped provider operation can be retried after restart only if its output was never durably checkpointed; no claim of external-provider exactly-once effects is made. Completed checkpoint batches are not inferred again. Embedded datastore execution serialization prevents concurrent provider work, while datastore lease predicates protect all committed effects from obsolete owners. Simultaneous multi-service epoch reconciliation is not supported by the existing single-owning-service embedded deployment contract; replacement process starts only after prior owner stops. RocksDB directory ownership independently excludes simultaneous embedded opens.

On replacement service startup, running enrichment jobs without a durable cancellation flag requeue at persisted source checkpoints; cancelled jobs stay cancelled, provider/validation failures require explicit exact retry. Obsolete worker tokens cannot commit. Promotion outcome is already terminal before HTTP readback, so restart cannot lose a committed policy epoch behind a cancelled job label. Explicit rollback is the same leased queue action and dependency-safe forward compensation, not schema rollback.

Canonical get_source also reports graph_policy_epoch and optional reviewed_enrichment_v1. This proof is generated from persisted validated terminal stage, full source/chunk snapshots and complete current endpoint revision map. It records separate original conversion vs pre-rollback opening epochs/revisions; final=opening+1. Conversion and rollback preserve source identity/generation, backing chunks and vectors. A later unchanged upload can update exact normalized-equivalent Markdown and provenance; its capture is independent of the immutable original upload request retained in the proof. The proof shape matches the staged importer's per-part evidence contract; a local wrapper must independently review server/workspace/document identity and COMPLETE ordered multipart inventory. This is not a distributed multipart commit or live importer installation.

Portable schema22 backup includes complete source checkpoint/plan/policy metadata, labelled note/entity embeddings, queued input/lease history, mutation journal and proposals. Extraction policy objects are not misclassified as vectors; optional empty private entity vectors serialize as absence. Full archive verification and fresh-target restore/reopen tests remain independently evidenced, not presumed from a version label. Old binaries must refuse schema22; no downgrade.
