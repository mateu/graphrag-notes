## Matching binary, clients and documentation

The native archive contains `graphrag`, the fictional starter sample and a
fixed public client/document bundle under `release/`. It preserves the sibling
imports used by benchmarking and native MCP clients. `VERSION`, `SOURCE-COMMIT`,
`PAYLOADS.json` and `PAYLOADS.sha256` identify and hash that bundle; external
`BUILDINFO` records the source/build commits, compiled inputs, target, runtime
requirements, binary/archive/payload hashes and explicit validation states.
No corpus, credentials, local client configuration, models, private evaluation
cases, or raw private reports are distributed.

A separate `graphrag-notes-v0.1.0-rc.3-clients.tar.gz` contains the identical
platform-neutral client/document payload without a native binary or starter
corpus. `CLIENTINFO.json` records its version, source commit and hashes; checksum-pinned flat identity sidecars cross-bind metadata bytes, selected release, archive, source and native payloads for the Python-free installer; both
are covered by `SHA256SUMS`. Linux clients can install this asset while native
Linux/Intel release acceptance remains deferred. Matrix assembly requires these
client artifacts to agree across all native packages.

The installer uses curl, tar and SHA tools. It installs clients/docs to
`$HOME/.local/share/graphrag-notes/releases/v0.1.0-rc.3` by default, preserving
edited configuration and starter notes. It refuses a modified existing version
bundle. Python **3.11+** is required to run the Python clients, separately from
binary installation. Use `--data-dir` to choose another bundle location.

After the candidate assets are published, pin the version explicitly:

```sh
curl -fsSL https://raw.githubusercontent.com/mateu/graphrag-notes/v0.1.0-rc.3/scripts/install.sh \
  -o /tmp/graphrag-install.sh
bash /tmp/graphrag-install.sh --help
bash /tmp/graphrag-install.sh --version 0.1.0-rc.3
export PATH="$HOME/.local/bin:$PATH"
graphrag --version
bundle="$HOME/.local/share/graphrag-notes/releases/v0.1.0-rc.3"
python3 "$bundle/scripts/refresh-openclaw-memory.py" --help
python3 "$bundle/scripts/mcp-capture-journal.py" --help
python3 "$bundle/scripts/benchmark-search.py" --help
```

For a Linux MCP client such as clawd, use the same version-pinned installer
download, then select only the clients/docs asset:

```sh
bash /tmp/graphrag-install.sh --version 0.1.0-rc.3 --clients-only
bundle="$HOME/.local/share/graphrag-notes/releases/v0.1.0-rc.3"
python3 "$bundle/scripts/refresh-openclaw-memory.py" --help
```

Default GitHub latest-release lookup excludes prereleases, so
`--version 0.1.0-rc.3` is required for both flows. Client-only installation keeps
the native executable, gateway configuration and corpus ownership separate.

Read the matching bundle's guides before applying refresh/capture commands.
Remote clients need an endpoint and environment credential, with capabilities
granted by the corpus owner. They do not need a local corpus or inference stack.
Use [shared MCP setup](../shared-mcp.md) for OpenClaw, Hermes and remote CLI
connections. An existing owner and client configuration remains separate from
the installed version bundle; upgrading binaries does not register another
OpenClaw plugin or change its model provider.

## Upgrade and rollback

Stop the owning service, quiesce clients and use the working binary to create
and verify a private portable backup before opening the corpus with rc.3.
Keep the original config/credential policy, client capture journals and refresh
state as private recovery material. Retain the exact working binary and its
source/build identity too: development deployments can share a version string
while supporting different schemas, so a version label alone is not rollback
evidence. Uploads/captures may outlive a disconnected
client; inspect owned jobs and retain uncertain requests before stopping the
owner. Restore an archive only into a fresh nonexistent database path.

rc.3 includes additive schema version **19**, including extracted entity
identity. Opening a corpus upgrades its schema. An older binary cannot safely
open that upgraded database. Rollback requires the pre-upgrade portable archive
restored into a new path, with the matching older binary/config; swapping the
binary against the upgraded path is not a rollback. Verify restored counts,
receipts, source generations and keyword retrieval before switching clients.
Default backups omit vectors and local file URIs; use `--include-embeddings`
when the recorded provider/model/dimension identity matches the intended owner.
See [backup operations](../operations.md) and
[upgrade instructions](../getting-started.md#upgrade-an-existing-installation).

## Release acceptance

The initial native target is **macOS Apple Silicon, macOS 15 or newer**.
Intel macOS and Linux native release/walkthrough acceptance remains tracked in
[#66](https://github.com/mateu/graphrag-notes/issues/66). Supported source builds
and retained workflow targets do not imply those native assets were published
or tested. Windows is outside this release scope.

The capture boundary was verified through the normal OpenClaw OpenAI OAuth
gateway with an interrupted HTTP proxy: explicit recovery produced one
canonical note and verified its pinned body/provenance. See the
[reviewed acceptance record](https://github.com/mateu/graphrag-notes/pull/102#issuecomment-6009389826).
This verifies the selected client/service boundary; automatic agent reuse and
human task-time measurements remain separate checks.

Before publication, record exact-head workspace tests, clippy, the six guarded
focused tests, offline daily workflow, native live walkthrough, private MCP
acceptance and local asset installation. After publication, independently
download HTTPS assets, verify checksum/BUILDINFO provenance, exercise a fresh
install and an upgrade preserving edited config/sample, then inspect the
installed clients and explicit keyword/hybrid/graph MCP paths. Keep public
evidence to fictional fixtures or sanitized counts/hashes/timings.

Preparation-time BUILDINFO remains immutable. Later published-install and
deployment results belong in a separate validation record linked here; do not
replace sealed assets to change a validation status. The publication and
deployment record is pending until those gates actually run.
