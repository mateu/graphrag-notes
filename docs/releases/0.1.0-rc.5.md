# GraphRAG Notes 0.1.0-rc.5

This candidate prepares a matched allocator comparison on the pinned SurrealDB 3.2.4 engine. It has not passed real-corpus RPC qualification, native release validation, publication or deployment. Published rc.4 and earlier tags/assets remain immutable. [#106](https://github.com/mateu/graphrag-notes/issues/106) and [#115](https://github.com/mateu/graphrag-notes/issues/115) remain open; this preparation does not claim either latency issue is resolved.

## Candidate scope

An optional CLI `allocator` feature forwards the optional DB feature to the upstream SurrealDB allocator. Library and CLI defaults remain unchanged. Official Apple Silicon release builds explicitly select it; macOS Intel and Linux release builds omit it and keep their existing allocation behavior. On macOS ARM this selects MiMalloc for Rust global allocations. It does not replace C/C++ RocksDB allocation. The pinned engine, queries, exact distance arithmetic, native record ordering, source/generation filters, application schema 21, graph policies, models and runtime concurrency remain unchanged.

The fictional native diagnostic matrix qualifies this as a candidate for a controlled real-corpus comparison. A retained memory/current-thread condition regressed, so fictional results do not establish a general tail improvement. Real-corpus acceptance must compare complete ordered records, native distances, pinned revisions/provenance, all first/warm observations, one/four lanes and every failure. A candidate must avoid new first/max tails and meet the declared retrieval-quality and latency gates before adoption. [Earlier vector experiments](../validation/exact-vector-experiments-106.md) and their rejected tails remain part of the evidence.

## Build identity and pending gates

[Release preparation](README.md) records the actual Cargo JSON compiler artifacts rather than a requested feature flag. The ARM seal requires the optional CLI/DB/SDK/core features and the exact MiMalloc package features; Intel/Linux seals require them absent. Sealing binds the compiler executable bytes to the selected binary. Packaging reparses the retained log, and BUILDINFO preserves its hash, native binary hash and normalized public feature facts. Version-only CLI metadata differs from the rc.4 comparison binary and is recorded explicitly; retrieval code remains the matched control.

The workspace and local lock packages use `0.1.0-rc.5`. External existing package versions remain unchanged. A new binary must be built and sealed from this candidate; historical compiled bytes cannot be relabeled rc.5. Source review/CI, matching optimized CLI builds, frozen real-corpus comparison, native functional workflows, actual published HTTPS fresh/upgrade installation and production rollout each need their own completed proof. Until those gates pass, this document is a preparation record.

Use `--features allocator` only for the Apple Silicon candidate release build. Keep private corpus contents, judgments, credentials and build paths outside release payloads. Preserve existing configuration, models, official importer state and historical validation assets during any later authorized rollout.
