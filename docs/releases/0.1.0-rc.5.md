## Rejected allocator experiment

The comparison used the same portable precision fix in both controls, identical Rust retrieval sources and frozen corpus/provider/cohorts. Complete ordered records, pinned readbacks and metrics matched across 400 quality attempts and 2,688 RPC attempts, with zero failures; full primary records and stored F64 vectors were preserved. These are preservation and agreement results, not evidence that partially judged retrieval is universally correct.

The declared gate required lower hybrid warm median/p95, unchanged or lower keyword timing, no new first or warm-maximum tail and zero failures in every group. No observation was replaced, excluded or retried.

| Comparison | Strict groups passed | Hybrid groups passed | Keyword groups passed | Hybrid warm p95 at most 1,000 ms |

| Traced | 28/32 | 24/24 | 4/8 | 22/24 |
| Ordinary RPC | 22/32 | 22/24 | 0/8 | 22/24 |

Every ordinary keyword group regressed. In the selected broad keyword case, one-lane warm median/p95 increased from 50.084/51.824 ms to 69.284/74.011 ms; four-lane median/p95 increased from 67.143/71.471 ms to 80.867/84.191 ms. Ordinary hybrid also retained two gate exceptions. Useful hybrid improvements do not waive those failures.

The [full aggregate](../validation/allocator-115-rejected.json) retains all 64 first/warm group summaries and unsuccessful gates. Each warm group contains 20 observations; median averages the two middle values and p95 uses nearest rank. First-observed values are not cold-start claims. Traced performance follows quality evaluation and remains separate from ordinary measurements. Nested backend elapsed time is not exclusive CPU and does not establish an allocator, SDK, HTTP or scheduling cause. Mac ARM results do not qualify Intel macOS or Linux. Historical native diagnostics, rejected tails, compiled commits, seals and the original failed precision-restore attempt remain preserved.

## Release source and provenance

Experimental CLI/DB allocator features and their four required locked packages are removed from this release source. CLI/library defaults remain unchanged, as do existing external package versions/checksums, exact engine distance arithmetic, native record ordering, source/generation filters, schema 21, graph policies, models and runtime concurrency. The accepted graph-only change in [#126](https://github.com/mateu/graphrag-notes/issues/126) plans compatible alias lookups freshly per entity, retains guarded fallback behavior, and fixes a later valid entity being omitted after another entity filled its mention page. Its scoped qualification is separate from the broader latency gates.

[Release preparation](README.md) requires retained successful Cargo JSON compiler artifacts, exact release profile/features and actual compiler executable bytes. Sealing, packaging and assembly bind the normalized system-allocator proof, log digest and binary hash to the selected source. Historical rc.4 packaging remains supported; missing or forged modern proof, enabled allocator features/packages, changed logs or substituted binaries are rejected.

Workspace and local lock packages use `0.1.0-rc.5`. The published integrated system-allocator binary was freshly built and qualified; the rejected allocator binary was not relabeled. Review/CI, optimized Apple Silicon build, controlled graph RPC/quality comparison, native functional workflows, published HTTPS installation and the deployment checks above have completed evidence. Future release or platform acceptance still requires its own evidence; these results do not qualify an unbuilt target or waive remaining latency gates.

Keep private corpus contents, judgments, credentials and build paths outside release payloads. Preserve configuration, models, importer state and historical validation assets. A full-vector rollback must use an explicitly verified precision-capable binary and restore into a fresh path; the historical published rc.4 parser is not a stored-F64 preservation control.
